# 0005.2. Fsync the output file and its parent directory before treating a write as durable

## Status
Accepted

## Context
[0005](0005-bounded-pipeline-backpressure.md) established a staged-write-then-rename pattern: the
consumer writes to a `.tmp` path and renames it into place only after the writer closes
successfully. That shape is the right one for *atomicity* - a reader never sees a half-written
file - but atomicity isn't the same thing as *durability*. A crash immediately after the rename
"succeeds" could still lose bytes that were buffered but never flushed to disk, or leave the
directory-entry update from the rename itself unpersisted, depending on filesystem and OS behavior.

## Decision
Added two explicit `fsync` calls. First, switched from consuming the Parquet writer with a method
that drops its inner file handle with no fsync access, to one that returns the underlying file
handle, and called `sync_all()` on it - flushing all data, including the Parquet footer - before
the rename. Second, immediately after the rename, opened the output's parent directory and called
`sync_all()` on it too, which is what makes the rename's own directory-entry update durable rather
than just atomic-looking.

## Consequences
The write path now closes the specific gap between "atomic rename" and "durable write" that a
write-temp-then-rename pattern alone doesn't cover. This test verifies the durability mechanism,
not an end-to-end crash-proof guarantee. It depends on the underlying filesystem and OS honoring
fsync semantics, which varies by environment and wasn't independently verified across every
platform this pipeline might run on.
