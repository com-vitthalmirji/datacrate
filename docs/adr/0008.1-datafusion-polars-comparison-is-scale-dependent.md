# 0008.1. Treat the DataFusion-vs-Polars comparison as scale-dependent, not a single verdict

## Status
Accepted

## Context
An earlier benchmark measured DataFusion beating Polars by roughly 2.85x on a large
(91GB, spill-forcing) aggregate query — see the join-and-scale work referenced by
[0008](0008-ballista-and-comet-benchmark-engines.md). Taken alone, that result reads as a general
"DataFusion beats Polars" claim, which is materially different — and less defensible — than what
was actually measured: one query shape, one scale, one host.

A dataset small enough to fit comfortably in the host's RAM (roughly 14GB against a 64GB ceiling,
versus the earlier 91GB spill-forcing dataset) needed testing separately before either comparison
could be trusted as anything more than a single data point.

## Decision
Ran the same aggregate query shape against a single-node-sized, comfortably-in-memory dataset,
five runs per engine to smooth out warm-up noise, with results cross-checked for correctness against
the same reference values across every run. Recorded both results as scale-dependent findings rather
than collapsing them into one verdict: Polars' lazy in-memory engine measured about 9% faster than
DataFusion at the small, in-memory scale, while DataFusion measured about 2.85x faster than Polars
at the large, spill-forcing scale.

## Consequences
Any public claim about DataFusion vs. Polars must state which regime it's talking about — the two
results are not in tension, they describe different operating points, and neither implies a general
winner. No dataset size between the two tested points was measured, so the actual crossover point
between "Polars wins" and "DataFusion wins" remains unknown; a claim that names a specific crossover
size would not be backed by evidence and must not be made.
